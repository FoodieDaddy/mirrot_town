# 镜中边城底层架构分析与优化指南

本项目本质上是一个**以数据库为中心的异步模拟器**，其难点在于如何让不可靠、高延迟的大模型（LLM）与要求实时、确定性的游戏引擎（Game Loop）完美融合。

如果想要完全复现本项目，并在此基础上加以优化，可以参考以下架构拆解与进阶优化指南。

---

## 一、 完全复现的四大基座

完全复现一个类似“斯坦福 AI 小镇”的系统，需要搭建以下四个核心基座：

### 1. 游戏与渲染引擎 (Frontend)
*   **当前选型**：`Phaser.js` (2D 渲染) + `React` (UI 交互)。
*   **核心实现**：
    *   基于 Tilemap（Tiled编辑器导出的 JSON）渲染地图。
    *   实现 A* 寻路算法，确保角色能绕开障碍物走到目标点。
    *   开发事件播放器：根据后端 WebSocket 传来的 `action_start` 和 `movement` 等事件，在前端进行状态同步和平滑补间动画。

### 2. 状态机与世界引擎 (Backend Game Server)
*   **技术建议**：Node.js / Go / Rust。
*   **核心实现**：
    *   **中央调度器 (Simulation Engine)**：通过虚拟时钟（GameTime）不断往前推演，管理所有角色的当前状态（坐标、动作、手头任务）以及环境状态。
    *   **异步队列**：由于大模型响应有延迟，角色在等待 LLM 结果期间需处于“发呆”或执行“挂起动作”的状态，等结果返回后再交由执行器（Action Executor）处理。

### 3. Agent 代理系统 (LLM Orchestration)
*   **技术建议**：自定义的 Prompt Builder 或 LangChain。
*   **核心实现**：
    *   **Action Loop (行为循环)**：根据环境感知 (`Perception`) 做出下一步动作（如走、看、使用物品）。
    *   **Dialogue Loop (对话循环)**：两个角色相遇时，开启独立的双人对话线程。
    *   **Memory & Reflection Loop (记忆与反思循环)**：在每日结算（或空闲）时，让大模型总结当天发生的事件，将短期记忆合并为长期记忆。

### 4. 数据与记忆持久化 (Storage)
*   **技术建议**：SQLite / PostgreSQL 结合 向量数据库。
*   **核心实现**：
    *   存储所有角色的设定（Profile）、事件流（Event Store，用于前端回放和数据统计）以及记忆流（Memory）。

## 二、 进阶优化方向

如果在复现时想解决现有架构中的性能与逻辑瓶颈，建议从以下几个方向进行降维打击式的优化：

### 💡 1. 大模型的“高低配”路由调度 (Cost & Latency Optimization)
*   **痛点**：当前架构下，即使是决定“下一步往哪走”这类简单逻辑，也频繁调用大模型，成本高、延迟大且容易造成卡顿。
*   **优化方案**：引入**多级决策树（Behavior Tree）**。像“种地”、“巡逻”、“回家”等日常既定路线，直接交由传统的行为树（纯代码逻辑）处理。只有当遇到突发事件（如突发火灾、有人搭话、发现新奇物品）时，才中断行为树，将上下文抛给 LLM 进行高阶决策。

### 💡 2. 引入真正的向量数据库 (Semantic Memory)
*   **痛点**：现有的记忆检索多依赖简单的关键词匹配或基础查询，当运行时间拉长（如一个月后），AI 难以有效回忆起久远但极其重要的细节。
*   **优化方案**：将所有对话和关键事件存入向量数据库（如 Qdrant 或 Milvus）。当 AI 见到某个人或物体时，先利用特征向量做余弦相似度检索（Cosine Similarity），提取最相关的 5 条记忆并注入到 Prompt 中，从而使角色的“记性”和“人情世故”更加连贯、真实。

### 💡 3. 从单体架构迁移到微服务/并发架构 (Performance)
*   **痛点**：Node.js 是单线程的，当世界中存在几十甚至上百个角色需要同时进行“思考”时，拼装 Prompt 和等待网络请求会严重阻塞主线程，导致整个世界运行卡顿。
*   **优化方案**：如果使用 Go 或 Rust 复现，强烈建议将 **游戏状态引擎 (Game Server)** 与 **Agent 思维引擎 (Agent Engine)** 解耦拆分。
    *   **Game Server**：只负责以高帧率运行物理碰撞和坐标同步。
    *   **Agent Engine**：作为独立的协程（Goroutine）或外部微服务集群，通过消息队列（如 RabbitMQ / Redis PubSub）异步接收世界状态，思考完毕后再将指令（Cmd）丢回给 Game Server 执行。

### 💡 4. 空间索引优化 (Spatial Indexing)
*   **痛点**：在计算“角色周围有什么”时，遍历整个世界的物品会带来极大的性能损耗。
*   **优化方案**：引入 QuadTree（四叉树）或简单的网格空间划分（Grid Spatial Partition）。角色只需获取自己所在 Grid 及其相邻 Grid 的物品，将计算量从 $O(N)$ 降低到 $O(1)$，从而支撑上万个物品的超大地图渲染和交互。

---

> **复现路径建议**：
> 建议先写一个纯代码（不带 LLM）的二维走路沙盒，将前后端联调打通；然后接入单一的 LLM 决策接口控制其中一个 NPC 测试链路；最后再引入记忆系统和多角色并发调度。工程量虽中等，但架构设计和调试的乐趣无穷。
